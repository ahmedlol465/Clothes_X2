# Seed Implementation

Files: `backend/src/database/seed.service.ts`, `backend/src/database/seed.cli.ts`,
`backend/src/database/demo-data.ts`, `backend/src/database/database.module.ts`

## 1. What the seeder does

`seedDemoDatabase(ds: DataSource)` inserts the demo dataset inside a **single
transaction**, in dependency order:

1. `seedUser` — `users`, `user_profiles`, `style_profiles` (incl. Style DNA
   dimensions/palette/category mix/evolution and `legacyStyleMemories`),
   `style_memories`, `subscriptions`
2. `seedWardrobe` — `wardrobes`, `wardrobe_items`
3. `seedOutfits` — `outfits`, `outfit_items` (slot + layer order), `outfit_feedback`
4. `seedPlanner` — `calendar_events`, `weekly_plans`
5. `seedShopping` — `shopping_items`
6. `seedDiscover` — `trend_styles`, `community_looks`

It returns a `{ created, skipped }` report with a row count per bucket.

## 2. Deterministic identity

Every seeded row that can be referenced has a fixed UUID in `demo-data.ts`
(`00000000-0000-4000-8000-0000000001xx/02xx/…`). Consequences:

- outfit → item links are stable and can be reconstructed on any machine;
- re-running the seed can detect "already present" by primary key;
- references survive a database reset because nothing is generated randomly.

Demo account and credentials are unchanged:
`karim@fashiontech.com` / `wardrobe2024` (legacy SHA-256 hash, transparently
upgraded to bcrypt by `AuthService.login` on first sign-in).

## 3. Idempotency

| Entity | Guard |
|---|---|
| user | `findOne({ email })` |
| user profile / style profile / style memory / subscription | `findOne` by owner (and memory by `userId + preference`) |
| wardrobe | `findOne({ id })` |
| wardrobe items (12) | `findOne({ id })` per row |
| outfits (6) | `findOne({ id })` per row |
| outfit items (18) | `findOne({ outfitId, itemId })` per link |
| feedback / events / products / trends / looks | `findOne({ id })` per row |
| weekly plan | skipped entirely when the table already has rows (the table is globally regenerated by `POST /planner/weekly`) |

Nothing is updated, overwritten, truncated or deleted by the seeder. A row that
already exists is counted as `skipped` and left byte-for-byte untouched, so
user-edited items, re-generated plans and created content survive a reseed.

## 4. Boot behaviour (`SEED_ON_BOOT`)

`SeedService.onApplicationBootstrap()`:

1. reads `app.seedOnBoot` (`SEED_ON_BOOT`, default `true`);
2. counts `users`;
3. seeds **only** when the users table is empty;
4. otherwise logs `Database already has users; demo seed skipped.`

So a populated database — including production — is never seeded implicitly,
and no code path can truncate or reset a table.

## 5. Explicit seed operation

```bash
cd backend
npm run seed            # ts-node src/database/seed.cli.ts
# DB_TYPE=postgres|mysql|sqlite selects the driver (default sqlite)
```

The CLI builds the same `DataSourceOptions` the API uses, connects, runs
`seedDemoDatabase`, prints the report plus the demo login, and always destroys
the connection.

### Defect fixed in this phase

`seed.cli.ts` declared `resolveMode()` twice, which failed
`npm run typecheck` with `TS2393: Duplicate function implementation`. The
duplicate was removed and the CLI now also prints a created/skipped summary.

## 6. Verified behaviour (real database, Node 22.20.0)

```
$ DB_TYPE=sqlite npm run seed
Connected to better-sqlite3. Seeding demo data...
{ "created": {}, "skipped": { "user": 1, "userProfile": 1, "styleProfile": 1,
  "styleMemory": 1, "subscription": 1, "wardrobe": 1, "wardrobeItems": 12,
  "outfits": 6, "outfitItems": 18, "outfitFeedback": 1, "events": 2,
  "weeklyPlan": 1, "products": 3, "trends": 2, "communityLooks": 4 } }
Seeded 0 new row(s), skipped 55 existing row(s).
```

Run a second time: identical output, `created: {}` — **no duplicates**.
Row counts after both runs are unchanged (see the data-integrity report).

## 7. Not verified

- Seeding against PostgreSQL/MySQL was not executed: no server is reachable in
  this environment (`DB_TYPE=postgres` would fall back to SQLite by design).
  The SQL is generated by TypeORM repositories, so driver portability is
  structural, not empirically tested here.
- The no-op migration (`1-initial-schema.ts`) is not exercised: development runs
  with `DB_SYNCHRONIZE=true`, which created the schema.
