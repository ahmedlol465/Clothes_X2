SECTION 3B — RECOMMENDATION RANKING AUDIT & REPAIR
================================================================================
Scope: make the best outfits appear first from meaningful, reliable signals,
without touching the Phase 1 score contract, the compatibility formula, the
learning architecture, or any user data.

Status: COMPLETE. Backend 47/47 tests pass (16 new). db.json untouched.


1. ROOT CAUSES OF THE RANKING DEFECTS
--------------------------------------------------------------------------------
Audit method: read every component of `src/recommendation-engine.js`, traced the
inputs each component reads (`scoring.js`, `style-memory.js`, `retrieval.js`,
`ai-engine.js`, `server.js`), and ran an offline diagnostic over the bundled
base wardrobe to observe the actual component values.

B — retrieval_relevance was scoring the occasion, not a request.
  `recommend()` called `buildRetrievalMap(pool, focus || occasion, ...)`. The
  Home path sends no focus, so the query became the occasion default 'casual'.
  `retrieval.rank('casual', ...)` gives a lexical 0.8 to any piece whose style
  contains "casual" (including "Smart Casual") and adds an occasion-context
  bonus. At weight 0.20 this was a tautological restatement of
  style_compatibility/occasion_fit — a large weight that could not discriminate
  between outfits that all had to satisfy the same occasion.

C — profile_match charged pieces for preferences the user never declared.
  `profileMatchSignal()` always added `total += 2` per piece (one colour check,
  one style check) even when only favouriteColors OR only preferredStyles was
  declared. A colours-only profile was therefore capped at 50% no matter how
  well the outfit matched; empirically it ranged 25–50 for the classic
  White+Casual profile instead of 0–100.

D — learned_affinity was compressed toward a neutral 50.
  `itemAffinity()` always averaged four sub-signals (colour, style, fabric,
  formality) and defaulted each missing one to 0.5. A single strong opinion
  (e.g. navy 0.9) was diluted by three 0.5s. `learnedAffinitySignal()` then
  averaged `itemAffinity` over *every* item in the outfit, including pieces the
  memory had no opinion about, pinning the component near 50 (observed 53–55)
  regardless of the opinion strength. A stored global formality lean
  (`occasions.formal`) additionally made `hasOpinionFor` return true for every
  item, activating a near-constant component everywhere.

E — freshness double-counted wear volume and penalised basics.
  `freshnessOf()` = 0.6*recency(lastWornLabel) + 0.4*volume(timesWorn).
  `timesWorn` is already the input to `scoring.recent_usage`, so a heavily-worn
  piece lost points twice. Because shoes and belts are worn all the time, they
  dragged the whole outfit's freshness down (observed a near-constant 64 across
  a fresh base wardrobe).

Non-defects confirmed (deliberately unchanged): the compatibility component and
its 11-factor formula; the 0–100 component scale; the `activeWeight || 1`
renormalisation and the divide-by-zero guards; the diversity and deterministic
exploration passes; and the documented profile/learned "amplification" overlap
with compatibility.personal_preference.


2. FILES CHANGED

Not changed: scoring.js (compatibility formula untouched), retrieval.js (kept
intact; still used by the stylist chat at server.js:742), ai-engine.js,

3. BEFORE / AFTER BEHAVIOUR
--------------------------------------------------------------------------------
B  Before: retrieval_relevance applied on every Home request at weight 0.20
           with query = 'casual'.
   After:  not requested → component drops out, weights renormalise over
           compatibility/freshness/profile/learned. A caller passing `focus` or
           `retrievalQuery` still gets real retrieval relevance.
   meta.retrieval: 'unavailable' → 'ok' | 'not_requested'.

C  Before: colours-only profile capped at 50 (empirical 25–50).
   After:  judged on the declared dimension(s); a fully-matching colours-only
           outfit reaches 100. A partial match is (hits / declared-checks).

D  Before: strength signal diluted to ~50–55.
   After:  a 0.9 navy opinion on a navy piece reports 90, and the components
           weight renormalises because un-opinionated pieces no longer drag it.
   A formality lean now varies per piece (rewards the dressier piece) instead
   of pinning a constant.

E  Before: freshness ≈ 64 constant (volume + recency, basics included).
   After:  pure last-worn recency over top/bottom/outerwear only; shoe/belt
           wear no longer moves the signal (test E3 asserts exactly this).


4. WEIGHTS & NORMALISATION STRATEGY
--------------------------------------------------------------------------------
The SCORE_WEIGHTS table is intentionally UNCHANGED
  compatibility 0.45, retrieval_relevance 0.20, profile_match 0.15,
  freshness 0.10, learned_affinity 0.10
(feedback-learning.test.js Test J pins this table, and the task forbids blind
weight replacement). The fixes change what each component MEASURES, not its
share — so the ordering signal gets cleaner without arbitrary retuning.

Normalisation: unchanged and re-verified. Components with no evidence set
hasSignal:false; `activeWeight` sums only the applied weights (|| 1 guard); each
reported weight is SCORE_WEIGHTS[key]/activeWeight; the applied weights are
asserted to sum to 1 (new test N1), with no NaN. The completeness ceiling from
scoring.js still caps incomplete outfits.

6. RISKS, LIMITATIONS & FOLLOW-UPS
--------------------------------------------------------------------------------
- meta.retrieval semantics changed ('unavailable' → 'ok'/'unavailable'/
  'not_requested'). Any consumer reading it should treat 'not_requested' as
  "no query", not as a failure. No in-repo consumer reads it.
- The /outfits/recommended endpoint has no search/query parameter, so on the
  automatic Home path retrieval is now correctly excluded. Retrieval is
  preserved for real requests: the stylist chat still calls retrieval.rank()
  directly (server.js:742), and any caller can pass `focus`/`retrievalQuery` to
  the engine. Re-enabling retrieval for an explicitly chosen (non-default)
  occasion would need the client to send a query/flag — out of scope here.
- Learned-affinity style matching still reads `styles[item.style]`, while chat
  may store garment nouns (e.g. "sneakers") that never equal a style label.
  The audit flagged this; fixing it would change the learning surface and was
  left out of scope per the task constraints. Ratings (the primary signal) and
  colour/fabric opinions flow correctly.
- A temporary opt-in diagnostic block (opts.diagnostic === true) still exists in
  the engine; it is read-only and off by default. It was left in place to keep
  this diff minimal.
- The historical reports RECOMMENDATION_ENGINE_EXPLANATION.txt (~lines 267, 960)
  still describe `match` as the engine score; they predate Phase 1 and were not
  edited.
