8. LEARNING BEHAVIOUR (feedback strength — STEP 5)
================================================================================
  The existing style-memory.js scale was inspected and PRESERVED unchanged
  (RATE_RATING = 0.09, RATE_CHAT = 0.04, BOUNDS = [0.02, 0.98]). §4 maps its
  signals onto that scale instead of inventing new weights:

    signal                    direction  magnitude / item (colours & styles)  cap
    ------------------------  ---------  ------------------------------------  -------------
    favourite (toggle → true) positive   +0.090  (≡ rating 5)                 clamp 0.02..0.98
    rating 5                  positive   +0.090                               clamp 0.02..0.98
    rating 4                  positive   +0.045                               clamp 0.02..0.98
    rating 3                  neutral    0 (row recorded, no movement)        n/a
    rating 2                  negative   -0.030                               clamp 0.02..0.98
    rating 1                  negative   -0.060                               clamp 0.02..0.98
    (fabrics move at 0.6x the colour/style delta — existing learnRating rule)
    comment text              existing learnChat (clause mining, 0.04 rate)

    duplicate handling : dropped before reaching the learner (§11).
    decay              : none (existing behaviour) — bounded instead by the
                         0.02/0.98 clamp + one event per payload per UTC day.
    one action cannot dominate: max delta per action is 0.09 of a 0..1 scale,
                         and the clamp stops any single direction at 0.98.
    This is preference learning / signal aggregation — NOT model training, and
    no machine learning is claimed anywhere in this section.

9. STYLEMEMORY INTEGRATION (STEP 4)
================================================================================
  - Learning is delegated to the pre-existing memoryStore.record() path, the
    same one POST /outfits/:id/feedback and /ai/chat already used. There is no
    second "style memory" system, no parallel store, no new learning function.
  - §4 supplies what that path was missing: correct item attribution
    (db.recommendationHistory fallback) and idempotent events.
  - New signals reach §3 automatically: engine.recommend() already receives
    `memory: memoryStore.read(db, userId)`, so favourites/ratings flow into the
    existing `learned_affinity` component (weight 0.10) with ZERO ranking
    changes.
  - style-memory.js itself was NOT modified (§2 instruction: do not modify).
    A malformed legacy memory row (e.g. `colors: null`) is therefore handled at
    the integration boundary: learning is attempted inside try/catch, the
    failure is logged (`[feedback] learning skipped: …`) and the event is still
    recorded; the response payload is built from a sanitised view
    (safeMemory) so it can never throw.

11. IDEMPOTENCY / DUPLICATE HANDLING (STEP 6)
================================================================================
  Mechanism: stable event id, derived deterministically from the payload:
      fb_<type>_<sha256(type|userId|outfitId|rating|comment|YYYY-MM-DD)[0..24]>
    - user-scoped, subject-scoped, payload-scoped, day-scoped (UTC window).
    - Follows the repository's crypto/hash conventions (store.sha256 uses the
      same node:crypto primitive); no new dependency, no extra table.
  Before learning: findFeedback(db, id) → hit ⇒ skip learning, skip the row,
    answer `duplicate: true` with the current learned state.
  Consequences: retries/double taps cannot multiply the signal; a deliberate
  identical re-rate on a later day still counts (new day ⇒ new id).
  Legacy rows carry no id, so they can never collide with a new event.
  History rows need no dedup: each GET legitimately creates a new impression,
  and growth is bounded by the 100-rows-per-user retention.

15. KNOWN LIMITATIONS (documented, not hidden)
================================================================================
  L1 "Shown" means the server returned it — there is no client acknowledgement
     of actual rendering (no impression ack / view / click producer exists).
  L2 No Flutter screen currently calls outfitFeedback()/toggleFavorite(); the
     Outfit History thumbs up/down is a local toast. The endpoints are ready
     and tested, wiring them is a frontend task (future integration point).
  L3 Un-favouriting records no negative signal (ambiguous undo vs dislike);
     rating 1-2 is the negative signal today. A dedicated rejection action is a
     future integration point.
  L4 Wear is NOT duplicated into a second event store: timesWorn/lastWornLabel
     already persist via PATCH and already drive §3's `freshness`. The Express
     wear path carries no outfit attribution, so a structured wear-event row
     would add no ranking value here (the TypeORM WearEvent entity is unused
     and documented instead).
  L5 No time decay on learned preferences (existing behaviour); bounded by the
     0.02/0.98 clamp + per-UTC-day idempotency + a 100-row/user history cap.
  L6 db.feedback remains unbounded (pre-existing pattern, kept for
     /admin/reports compatibility); only the NEW history array has retention.
  L7 Attribution of feedback to a generated outfit depends on that row still
     existing in the 100-per-user history window; beyond it, items resolve to
     [] and learning degrades to exactly the pre-§4 behaviour (no crash).
  L8 Idempotency window is one UTC day: the same user/outfit/payload on the
     same day counts once. A deliberate identical re-rate later still counts.
  L9 NestJS entities (recommendations, recommendation_feedback, outfit_feedback,
     wear_events, style_memories) exist but remain unwired — documented only,
     per the primary-runtime rule.
  L10 The seed's legacy `styleMemory` (singular) row is still dead data; fixing
     or removing it would be unrelated cleanup and was out of scope.
  L11 Jest (npm test) could not run: backend/node_modules is absent. The suite
     uses node:test so it runs with zero installs.
