========================================================================
PHASE 3 — OUTFIT RATING (UI + PERSISTENCE, NO LEARNING)
========================================================================
Scope: let a signed-in user give an outfit a 1–5 star rating, persist it on
the backend, and show the saved value again when the outfit is reopened.
Explicitly OUT of scope: learning. A rating must NOT move StyleMemory,
compatibility, ranking or any recommendation. (That is Phase 4.)

------------------------------------------------------------------------
1. DESIGN DECISION
------------------------------------------------------------------------
The only existing rating path was `POST /outfits/:id/feedback`, which LEARNS
(it calls history.applyFeedback -> memoryStore.record). Reusing it as-is would
violate "persistence without learning", and adding a flag to it would mean
editing the learning path the Phase 2 suite exercises.

Chosen: Plan A — a NEW, persistence-only pair of endpoints that reuse the
existing `db.feedback` storage and its helpers, and never touch learning:

    POST /outfits/:id/rating   body { rating: 1..5 }  -> { ok, outfitId, rating }
    GET  /outfits/:id/rating                          -> { outfitId, rating|null }

The existing /feedback and /favorite routes are untouched.

------------------------------------------------------------------------
2. BACKEND CHANGES
------------------------------------------------------------------------
backend/src/recommendation-history.js
  - New "outfit ratings" section (persistence only):
      RATING_SOURCE = 'outfit_rating'
      isValidRating(value)  -> true only for a whole JSON number 1..5
      ratingEventId(...)    -> stable id `fb_rating_<hash(user,outfit)>`
                               (NOT day-scoped, so one row per user+outfit)
      saveRating(db, ...)   -> insert, or update the one existing row in place
      readRating(db, ...)   -> the user's current rating, or null
  - Reuses feedbackRows/findFeedback/isoAt/hashOf. Never calls
    memoryStore.record. Exported new names; module header documents the add.

backend/server.js
  - POST /outfits/:id/rating: validates via history.isValidRating; 400 on
    anything that is not an integer 1..5; saves under the bearer user; persist().
  - GET  /outfits/:id/rating: returns the bearer user's saved rating or null.
  - Both placed with the other §8.5 outfit routes; last segments are distinct
    so they never collide with GET/POST /outfits/:id*.

3. FLUTTER CHANGES
------------------------------------------------------------------------
lib/core/icons/sw_icon.dart
  - Added SwIcon.star (outline) and SwIcon.starFill (filled) glyphs.

lib/core/api/smartwardrobe_api.dart
  - outfitRating(id) -> int?  (GET)

                             POST, updates the map, returns success

lib/features/outfits/perfect_match_screen.dart  (the shared outfit details
screen, opened from Home, the recommendation rail, Saved, Favorites, History)
  - initState loads the saved rating for widget.outfit.id.

    five _Star buttons, and a spinner while a save is in flight.
  - _Star: filled vs outlined + primary vs tertiary colour; Semantics

  - On tap: submitRating, then a snack bar ("saved" / "could not save").
  - Only rendered when the outfit has a non-empty id (history demo rows with
    no id hide the control).

4. CONSTRAINTS HONORED
------------------------------------------------------------------------
- SCORE_WEIGHTS, compatibility/ranking formulas, the match alias: unchanged.
- No learning: ratings never reach memoryStore; verified by tests G and H.
- No scoring/retrieval/profile/freshness change; no new data collection
  (reuses db.feedback), no migration, no duplicate feedback system.
- User-scoped: rows keyed by bearer userId; verified by test D.
- Persisted server-side (restart-safe): verified by test F + live smoke test.
