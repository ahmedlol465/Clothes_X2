--- 5. EXISTING RETRIEVAL SYSTEM (CRITICAL) ---

FILE: backend/src/retrieval.js
- Two-stage wardrobe retrieval: Stage 1 (local scoring) → category-balanced shortlist → Stage 2 (LLM sees shortlist)
- Inputs: query (string), wardrobe (array), opts {weather, occasion, limit, slots, excludeIds}
- Outputs: Array<{item, score, semantic, lexical, context}> sorted + balanced
- Embeddings: Uses @huggingface/transformers with model 'Xenova/all-MiniLM-L6-v2' (384 dims) when available
- Falls back to lexical scoring if embeddings unavailable (EMBEDDINGS=off or model fails)
- Semantic retrieval: Yes - cosine similarity on embeddings with blend of lexical+context+slot bonus
- Lexical retrieval: Yes - token matching with field weights (name:1, color:0.85, others 0.6) + coverage
- Context support: Yes - occasion via tax.occasionTarget() and formality, weather via climateBonus
- Supports clothing slots/categories: Yes - tax.slotOf() for filtering/balancing; balanced by slot (top/bottom/shoes/outerwear/accessory with quotas)
- Uses embeddings: Yes, cached per item (vectors Map by itemId, invalidated by fingerprint of item attrs)
- Embeddings source: Generated on-the-fly via transformers.js pipeline from item text (itemText combines name,color,style,category,material,pattern,season)
- Called from: server.js stylistContext() calls retrieval.rank(message, wardrobe, {...limit:30}), ai-engine uses retrieval.lexicalScore() for focus
- Existing dependents: server.js (stylist), ai-engine.js

CONCLUSION: EXISTING RETRIEVAL SYSTEM IS PRESENT AND FULLY FUNCTIONAL. The future Recommendation Engine MUST reuse this capability - do not replace it.

--- 6. EXISTING AI / ML AUDIT ---

CLOTHING VISION MODULE: backend/src/clothing-vision/
- index.js: Main analyzeClothingImage() - takes image bytes, runs encoder+classify+color
- encoder.js: Uses @huggingface/transformers with Marqo/marqo-fashionCLIP (512 dims, dtype q8) - loads once
- classify.js: Zero-shot classification with clothing vs non-clothing gate (margin + clothing mass)
- color.js: Color analysis in CIELAB/LCh
- prompts.js: Label vocabularies, GATE thresholds (clothingMargin 0.01, clothingMass 0.4), model config
- Gate logic: Requires both margin and mass above thresholds; rejects non-clothing with reasons

AI ENGINE: backend/src/ai-engine.js
- Beam search over outfit slots (BEAM_PER_SLOT=6, BEAM_WIDTH=8)
- Uses retrieval.lexicalScore() for focus
- Integrates scoring.js, memoryStore, taxonomy
- generateOutfits() builds combinations respecting slots, climate, occasion
- remixOutfit(), chatReply() for stylist

SCORING: backend/src/scoring.js
- 11-factor compatibility model (as per README comments)
- Factors include color harmony, formality, season, material, fit context, etc.
- Reads StyleMemory, weather, styleProfile

STYLE MEMORY: backend/src/style-memory.js
- Learns user preferences from feedback
- Affects ranking/recommendations

FASTAPI AI SERVICE: ai-service/main.py (separate service, optional)
- /analyze-clothing, /chat, /generate-outfit endpoints
- Simpler rule-based implementation; can proxy to it if AI_SERVICE_URL set

MODELS:
1. Marqo/marqo-fashionCLIP (512 dims) - clothing vision classification
2. Xenova/all-MiniLM-L6-v2 (384 dims) - semantic retrieval
3. Also references YOLOv8n.pt in README/handoff context (not in this repo's backend/models? Let us check)

EMBEDDINGS:
- Generated on-the-fly via transformers.js pipelines
- Cached in memory (retrieval.js: vectors Map, textCache Map; clothing-vision loads encoder once)
- No persistent vector DB (pgvector) - uses in-memory + file store
- WardrobeItem entity has embeddings: number[] | null (TypeORM entity) - field exists in schema

INFERENCE: Performed on demand; clothing-vision encoder init() loads once; retrieval warmup() available
REUSE: clothing-vision gate, encoder, classify logic; retrieval system (MUST reuse); scoring engine; ai-engine structure

--- 19. RISKS / CONSTRAINTS ---

ACTUAL RISKS (evidence-based):
1. Dual backend implementations (Express server.js + NestJS) - could cause confusion; server.js is primary per README
2. File-based store (server.js) vs TypeORM - different persistence models; Recommendation/Feedback entities exist in TypeORM but server.js uses JSON arrays
3. Distributed recommendation logic - generateOutfits in ai-engine, retrieval in retrieval.js, scoring in scoring.js - refactoring needs care to avoid breaking existing endpoints (/outfits/recommended works)
4. Embeddings generation on-the-fly - could be slow on first request without warmup (retrieval.warmup() exists)
5. No persistent vector DB - in-memory vectors cached; fine for current scale
6. Behavioral signals: clicks/views not tracked - only explicit actions (wear, favorite, feedback)
7. Recommendation history entities exist but may not be fully wired in Express server.js paths
8. Memory constraints: transformers.js models load in memory (Marqo-FashionCLIP + MiniLM) - as noted in handoff, running multiple servers causes memory pressure
9. Existing /outfits/recommended endpoint is production code - must not break its contract
